# APIとデータ更新の設計

## 責務

- Auth0: ログインとID管理。Workerは署名、issuer、audience、有効期限、subjectを検証する。
- Cloudflare Worker: APIの認証、入力検証、所有者単位の操作。
- D1: デバイス、APIキーのハッシュ、ユーザー設定。
- React: 保存済みデータの表示。手動更新・30秒間隔の自動更新はGETだけを実行する。

端末の計測値はAPIキー付きPUTで受け取る。画面で更新しても計測時刻を更新しない。
PUTのis_chargingはbooleanと既存クライアントの0/1を受け付け、D1では0/1に正規化する。
省略した任意の計測値はnullとして保存する。

公開先は https://batt.ryuya-dev.net 、Workerは batterysync。
Auth0のissuer、audience、カスタムクレームの名前は認証プロバイダ側の契約であり、
公開URLの変更だけで書き換えない。Auth0アプリのCallback/Logout/Web Originsには新しいoriginの登録が必要。

## APIの防御

API全体で実際のボディサイズを16KiBまでに制限する。
Cloudflareのレート制限は一般APIでIP単位300回/分、連携・削除・キー発行で20回/分。
カウンタはCloudflare拠点ごとであり、グローバルな厳密上限ではない。
APIキーは計測値送信用。デバイス削除はAuth0ログインが必須（旧APIキーDELETEからの変更）。
ユーザー用APIではMachine-to-Machineのsubjectを受け付けない。
所有者を指定したSQLと署名済みテスト用JWTを使い、別ユーザーのデータ操作を回帰検証する。

## 本番スモークテスト

`node scripts/smoke.mjs https://batt.ryuya-dev.net` で公開ページ、未認証API、無効なJWT、
CORSプリフライトを確認する。実ユーザーのデータを作成・更新・削除しない。
認証後の操作は実ログインによる追加確認が必要。

## エラー

不正な認証は401、不正JSON・入力は400、所有する対象が存在しない場合は404。
内部障害は500、外部認証サービスの障害は502/503。DB障害を認証失敗と混同しない。
API応答はno-store。APIのナビゲーションにもSPAのHTMLを返さないようWorkerを先に実行する。

## アカウント削除

Management APIトークンの取得後、D1の4テーブルをbatchで削除する。
D1失敗時はAuth0ユーザーを削除しない。Auth0削除が失敗した場合は成功を返さず、ログインが残るため再試行する。
Auth0とD1をまたぐ単一トランザクションではない。Auth0側の失敗時にはアプリデータのみ削除済みとなる。

## アカウント連携

両方のアクセストークンを検証し、メール確認はトークンに存在するとは限らないemailクレームではなく
Management APIのプロフィールから行う。確認済みメールが一致することを要求する。
Auth0の連携ではD1データが移行されないため、連携先にデバイスまたはAPIキーがある場合は409で止める。
ユーザーをまたぐデータ統合はまだ実装していない。

## 検証と運用上の境界

`pnpm test` は認証エラー、入力不備、任意値省略、CORS、削除の障害を回帰検証する。
`pnpm check` はlint、型検査、ビルドを実行する。
ローカルD1マイグレーションとWrangler dry-runを併用する。

0001は新規DB用の初期スキーマであり、既存テーブルの構造を変更しない。
既存本番DBのスキーマ確認とAuth0実ログイン・連携の通し検証は別途必要。
Auth0連携の再認証と連携後セッション切り替え、ユーザー間データ統合は引き続き改善対象。
